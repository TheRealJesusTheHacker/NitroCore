# NitroCore Security & Functionality Audit ("Bug Bounty")

**Date:** 2026-09-25
**Scope:** `NitroCore/main.py`, `NitroCore/source/modules/*.py`, `NitroCore/source/utils/*.py`, `NitroCore/source/gui/*.py`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `NitroCore/setup.py`, `NitroCore/nitrocore.spec`, `SECURITY.md`
**Method:** Line-by-line static review. No code was changed.
**Auditor note:** This is a Windows-targeted application reviewed on Linux. Anything marked *(verify on Windows)* could not be executed here — treat those as "needs a Windows test pass," not as confirmed bugs.

**Headline:** No critical remote-code-execution or credential-leak issues found. The real risks are all in the safety-UX layer: destructive actions that run with no confirmation, a restore-point gate that doesn't actually gate, and one recursive-deletion path that needs hardening against symlink/junction escapes.

---

## HIGH

### H-1 — Pip-Boy easter egg runs the full destructive pipeline with zero confirmation
**File:** `NitroCore/main.py:178` (`_run_pipboy_purge`), button wired at `main.py:125-126`
**Description:** After 7 clicks on the title, the UI switches to Pip-Boy mode, which contains a button labeled "INITIATE SYSTEM PURGE AND OVERCLOCK". Clicking it launches the *entire* optimization pipeline for real: registry edits (`registry.apply_all()`), temp deletion, browser cache wipe, `cleanmgr`/`DISM`, **stopping the Windows Update service** (`services.optimize_all_services()`), and power-plan changes. There is no confirmation dialog, no restore-point prompt, no preview-mode check, and no busy guard — the normal UI gates (`_run_async` → `_prompt_restore` → `_set_busy`) are completely bypassed.
**Impact:** A user idly clicking an obvious joke button irreversibly modifies their system (including disabling Windows Update) with no warning and no undo path. Double-clicking launches two concurrent full pipelines (registry writes, file deletions, service stops racing each other).
**Fix:** Route the purge through the same `_run_async`/`_prompt_restore` path as everything else, or at minimum: show the RestorePointDialog, honor `Config.DRY_RUN`, and disable the button while a run is in flight. Consider removing real destructive actions from an easter egg entirely.

### H-2 — "Clean Old Downloads" permanently deletes user files with one click, no confirmation, no restore prompt
**File:** `NitroCore/source/modules/disk_cleanup.py:88` (`clean_downloads`), wired at `NitroCore/source/gui/tabs.py:594-595` (`_run_disk_downloads`)
**Description:** The button calls `_run_async("Downloads Cleanup", ...)` with `require_restore=False` (compare: registry/services/disk-system all pass `require_restore=True`). There is no "are you sure" dialog, no restore-point offer, no Recycle Bin — `os.remove()` is final. Deletion is driven purely by file mtime > 30 days, so installers, documents, photos, or project files the user still wants are deleted if untouched for a month. Directories are recursed and emptied dirs removed.
**Impact:** Single-click, silent, irreversible user data loss.
**Fix:** Add `require_restore=True` (or a dedicated confirmation dialog naming the file count), move deleted files to the Recycle Bin (`winshell`/`SHFileOperation`) instead of `os.remove`, and consider basing the heuristic on more than mtime or letting the user pick the retention window (the `retention_days` parameter exists but the GUI hardcodes 30).

### H-3 — Recursive temp purge may follow junctions/symlinks outside the target tree *(verify on Windows)*
**File:** `NitroCore/source/modules/temp_files.py:33-47` (`_fast_dir_purge`); same pattern in `NitroCore/source/modules/disk_cleanup.py:88-125` (`_purge_old_files`)
**Description:** The recursion guard is `entry.is_dir(follow_symlinks=False)`. Whether Windows directory *junctions* (common in temp/profile trees) report `False` here depends on CPython's reparse-point handling and must be verified on a real Windows host. If a junction inside `%TEMP%` (or Downloads) is treated as a real directory, `_fast_dir_purge(entry.path)` will `os.scandir` *through* it and `os.remove` files outside the intended tree. There is also a TOCTOU gap between the `is_file`/`is_dir` check and the `os.remove`/`os.rmdir` call.
**Impact:** Potential deletion of files outside the temp/Downloads directories — the worst-case shape of a cleanup-utility bug.
**Fix:** Explicitly skip reparse points before recursing: `entry.is_junction()` (Python 3.12+) or an `os.lstat()` attribute check, in addition to `follow_symlinks=False`. Re-verify with a test junction on Windows.

## MEDIUM

### M-1 — Restore-point gate is advisory: a failed restore point doesn't stop the pipeline
**File:** `NitroCore/source/gui/tabs.py:453-475` (`_create_restore_then`)
**Description:** When the user picks "Create & Continue," the continuation runs unconditionally — even when `create_restore_point()` returns `(False, ...)` (System Restore disabled, 24h frequency limit, timeout). The failure is only a log line with "warning" styling, then the destructive run proceeds.
**Impact:** The safety net the user explicitly asked for silently doesn't exist, and they proceed believing they're protected.
**Fix:** If the user chose "create" and creation fails, do not run the continuation. Re-prompt with the failure reason and offer "Abort / Continue without restore point / Retry."

### M-2 — Gaming profile stops Windows Update and BITS with no security warning
**File:** `NitroCore/source/modules/services.py:15-17` (`services_to_optimize = ["wuauserv", "BITS", "WSearch"]`)
**Description:** `optimize_all_services()` stops `wuauserv` (Windows Update) and `BITS` and sets both to Manual startup. Patching effectively stops until something re-enables it. The services tab copy mentions stopping "Update" but nothing warns that this degrades OS security patching. The Cybersecurity profile correctly keeps Update alone.
**Impact:** Users trading away security updates for FPS without understanding the trade.
**Fix:** Add an explicit warning in the Gaming services description and in the result log ("Windows Update set to Manual — re-enable to receive security patches"), or stop short of touching `wuauserv`/`BITS` and only tune `WSearch`.

### M-3 — Every "Apply Power Plan" click clones another "Ultimate Performance" scheme
**File:** `NitroCore/source/modules/performance.py:88`
**Description:** `powercfg -duplicatescheme <ultimate-guid>` is executed unconditionally before `powercfg /s`. `duplicatescheme` always creates a *new* scheme entry — repeated clicks accumulate duplicate "Ultimate Performance" power schemes in `powercfg /l`.
**Impact:** Power-scheme list pollution; confusing for users and for the app's own scheme detection.
**Fix:** Check `powercfg /l` output for the Ultimate Performance GUID first and only duplicate when absent.

### M-4 — Registry tweaks overwrite whole values with no per-value backup
**File:** `NitroCore/source/modules/registry.py:155-173` (`_optimize_performance`)
**Description:** `UserPreferencesMask` is overwritten with a hardcoded 8-byte blob (`b'\x90\x12\x03\x80\x10\x00\x00\x00'`). That mask encodes accessibility and UI settings (high contrast, etc.) — a user with non-default settings loses them silently. No old values are recorded anywhere; the only recovery path is a system restore point. `_set_registry_value` also creates missing keys via `CreateKeyEx`, which is fine for these paths but means typos in future tweaks would silently create junk keys.
**Impact:** Loss of user accessibility/visual settings with no in-app undo.
**Fix:** Read and stash each value's pre-change bytes in the log/preview output (and ideally in a JSON "undo" file under `%APPDATA%\NitroCore`) with a one-click "restore previous values" action.

### M-5 — `setup.py` points at a `src/` layout that doesn't exist
**File:** `NitroCore/setup.py:57-58`
**Description:** `find_packages(where="src")` + `package_dir={"": "src"}`, but the code lives in `source/`. `pip install .` therefore builds and installs an *empty* package. Also: placeholder `url`/project URLs (`your-username`), `author_email="support@nitrocore.io"`, and no `VERSION` file (falls back to `"1.0.0"`, drifting from `__version__`).
**Impact:** Broken sdist/wheel distribution; version metadata lies.
**Fix:** Point at `source/` (or rename to `src/`), fill in the real repo URL, and add the `VERSION` file (or single-source the version from `source/__init__.py`).

### M-6 — Release pipeline installs unpinned build dependencies for an admin-elevation binary
**File:** `.github/workflows/release.yml:21-22`, `NitroCore/requirements.txt`
**Description:** `pip install pyinstaller` (unpinned) plus `requirements.txt` using `>=` ranges. The produced `.exe` requests admin elevation (`nitrocore.spec:45`, `uac_admin=True`), so a compromised or drifted dependency lands directly in a privileged binary. No hash pinning (`--require-hashes`) anywhere.
**Impact:** Non-reproducible builds; supply-chain drift in a high-privilege artifact.
**Fix:** Pin exact versions (and hashes) in `requirements.txt` / a constraints file, and pin the pyinstaller version in `release.yml`.

### M-7 — Release binary is unsigned and UPX-packed
**File:** `NitroCore/nitrocore.spec:35` (`upx=True`), `nitrocore.spec:42` (`codesign_identity=None`)
**Description:** No code signing → Windows SmartScreen will flag/warn on every download. UPX packing is a known AV-heuristic trigger and occasionally breaks PyInstaller onefile binaries.
**Impact:** User trust + AV false-positive risk on the exact binary users are told to trust with admin rights.
**Fix:** Sign releases (even a cheap OV cert), publish the SHA256SUMS (already done — good), and consider dropping UPX.

## LOW

### L-1 — Non-Windows launch crashes with `AttributeError` instead of a clean message
**File:** `NitroCore/main.py:198-205` (`run()`)
**Description:** `is_admin()` safely returns `False` off-Windows, but the next line calls `ctypes.windll.user32.MessageBoxW(...)` unguarded — `ctypes.windll` doesn't exist on Linux/macOS, so it throws `AttributeError`. (The `--dry-run` headless path skips this and works fine.)
**Fix:** Reuse the existing `show_blocking_message()` helper instead of calling `ctypes.windll` directly.

### L-2 — Logger docstring claims async QueueHandler logging that isn't implemented
**File:** `NitroCore/source/utils/logger.py:52-55`
**Description:** Comment block "3. QueueHandler Wrap (The Secret to Max Multi-Threading Performance)" — no `QueueHandler`/`QueueListener` exists; handlers are attached directly. Misleading for future maintainers reasoning about thread-safety.
**Fix:** Either implement the queue-based logging or delete the comment.

### L-3 — `hash_password_secure` is single-round SHA-256, not a password KDF
**File:** `NitroCore/source/utils/helpers.py:34-44`
**Description:** `SHA256(salt + password)` with no stretching. Currently unused by the app (no callers found), but the name promises more than it delivers.
**Fix:** If it's ever used for real passwords, switch to `hashlib.pbkdf2_hmac` (≥200k iterations) or bcrypt; otherwise mark it clearly as non-password use.

### L-4 — `ProgressPanel.reset()` doesn't stop a running indeterminate bar
**File:** `NitroCore/source/gui/progress_panel.py:105-110`
**Description:** `start(label, total_steps=1)` calls `self.bar.start(12)`; `reset()` zeroes the value and hides the widget but never calls `bar.stop()`, leaving the animation callback alive.
**Fix:** Call `self.bar.stop()` in `reset()`.

### L-5 — Closing the window mid-run raises `TclError` in the worker thread
**File:** `NitroCore/source/gui/tabs.py:524-538` (`_execute_async`), `NitroCore/source/modules/async_worker.py`
**Description:** The worker's `on_complete` calls `self.root.after(0, ...)` directly. If the window was destroyed first, this raises `TclError` inside the worker thread (noisy traceback; the second `on_complete(None)` call in the except path raises again and kills the thread).
**Fix:** Guard with `self.root.winfo_exists()` before scheduling, or wrap the `after` call in try/except `tk.TclError`.

### L-6 — `_stop_service_safely` doesn't wait for the service to actually stop
**File:** `NitroCore/source/modules/services.py:104-125`
**Description:** `ControlService(SERVICE_CONTROL_STOP)` is fire-and-forget; the function reports "Stopped Successfully" immediately, possibly before the service reaches `SERVICE_STOPPED`.
**Fix:** Poll `QueryServiceStatus` with a short timeout and report the observed end state.

### L-7 — `cleanmgr` failure is swallowed silently before the DISM fallback
**File:** `NitroCore/source/modules/disk_cleanup.py:76-96` (`clean_system_files`)
**Description:** If `cleanmgr` exits non-zero, execution falls through to DISM with no log of *why* cleanmgr failed.
**Fix:** Log `proc.returncode` and stderr before falling back.

### L-8 — Dead code / metadata drift
- `nitrocore.spec` lists `yaml` in `hiddenimports`, but nothing imports yaml (dead entry).
- `main.py` defines `show_blocking_message()` but `run()` doesn't use it (see L-1).
- `source/utils/helpers.py` utilities (`sanitize_input`, `fast_memoize`, etc.) have no callers — unused surface area.
- No `VERSION` file; `setup.py` silently falls back to `"1.0.0"`.
- `main.py` title says `v1.0.1` while `source/__init__.py` and `source/gui/init.py` say `1.0.0` — pick one source of truth.

### L-9 — Pip-Boy mode is one-way; click counter never resets
**File:** `NitroCore/main.py:207-213` (`_handle_secret_clicks`), `draw_dashboard`
**Description:** Once triggered there is no path back to the normal UI without restarting, and every further title click re-triggers the redraw + beep.
**Fix:** Reset `CLICK_COUNTER` after triggering; add a way back (e.g., clicking the Pip-Boy header returns to normal mode).

### L-10 — Preview recorder assumes serialized runs; Pip-Boy purge bypasses the busy flag
**File:** `NitroCore/source/utils/preview.py` (module docstring), `NitroCore/main.py:178`
**Description:** The process-wide `_PreviewRecorder` is safe only because the GUI serializes runs via `_busy`. The Pip-Boy purge path never sets the busy flag, so concurrent runs could interleave preview entries. (Covered by the H-1 fix — route it through `_run_async`.)

## Explicitly checked and CLEAR

- **Command injection:** all `subprocess` calls use static argument lists; the single `shell=True` path (`registry.py:135`, wmic fallback) interpolates only the static string with `%computername%` expanded by cmd.exe — no user input reaches a shell. `restore_point.py` escapes single quotes by doubling for the PowerShell single-quoted string, and the description is internally generated, not user-controlled.
- **Network activity:** no `socket`/`urllib`/`requests`/`http.client` usage anywhere — `SECURITY.md`'s "no network connections" claim is accurate as of this review.
- **Secrets in code/logs:** none found; log paths contain only `%APPDATA%` paths and exception text.
- **Registry hive safety:** all writes target `HKCU` (per-user visual effects) — no `HKLM` writes anywhere in the tweak list.
- **Privilege handling:** the app requires admin up front (`main.py` admin gate + `uac_admin=True` in the spec) rather than attempting silent elevation; service/registry failures degrade to readable messages.
- **CI workflows:** `actions/checkout@v4` and `actions/setup-python@v5` are pinned to major versions (acceptable); `release.yml` uses minimal `permissions: contents: write` and publishes SHA256SUMS (good). Remaining concern is M-6 (unpinned build deps).
- **Preview/dry-run integrity:** every mutating module checks `Config.DRY_RUN` at call time and records instead of executing; the GUI preview toggle is disabled while a run is in flight (`_set_busy`), so mid-run toggling can't half-apply a pipeline. The headless `--dry-run` path correctly skips the admin gate and single-instance mutex.
